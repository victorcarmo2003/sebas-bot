Visão geral do contrato

Um módulo Sebas é um pacote npm pequeno com um manifest e um punhado de arquivos compilados, rodando isolado numa worker_thread.

As três peças

Manifest

sebas.module.json na raiz do repo — declara id, capabilities, entrypoints e permissões pedidas. Ver API → Manifest.

Entrypoints

Um arquivo .js compilado por capability declarada — o core carrega sob demanda. Ver API → Capabilities.

Context (SDK)

SebasModuleContext — o único jeito do seu código tocar storage/rede/Discord/IA, tudo validado contra as permissões concedidas. Ver API → Module SDK.

Como o core executa isso

  1. Lê sebas.module.json, resolve os paths de entryPoints pra absolutos.
  2. Sobe uma worker_thread nova, passa esses paths pra dentro.
  3. Dentro da worker, um dispatcher genérico (runner.ts) importa o entrypoint certo sob demanda e chama o método correspondente à capability (handleRequest, run, handleCommand, callTool, checkGate).
  4. Toda chamada de ctx.* dentro da worker vira uma mensagem RPC de volta pro processo principal, que checa permissão e executa de verdade.
Seu módulo nunca tem acesso direto a filesystem, rede ou child_process do host — só o que passa pelo ctx, e só o que foi concedido.

Duas formas de existir

Onde moraDentro do monorepo sebas-botRepositório git próprio, público

Contract overview

A Sebas module is a small npm package with a manifest and a handful of compiled files, running isolated inside a worker_thread.

The three pieces

Manifest

sebas.module.json at the repo root — declares id, capabilities, entrypoints, and requested permissions. See API → Manifest.

Entrypoints

One compiled .js file per declared capability — core loads them on demand. See API → Capabilities.

Context (SDK)

SebasModuleContext — the only way your code touches storage/network/Discord/AI, all validated against what was granted. See API → Module SDK.

How core runs this

  1. Reads sebas.module.json, resolves entryPoints paths to absolute.
  2. Spawns a new worker_thread, passes those paths in.
  3. Inside the worker, a generic dispatcher (runner.ts) lazily imports the right entrypoint and calls the method matching the capability (handleRequest, run, handleCommand, callTool, checkGate).
  4. Every ctx.* call inside the worker becomes an RPC message back to the main process, which checks permissions and actually executes it.
Your module never has direct access to the host's filesystem, network, or child_process — only what flows through ctx, and only what was granted.

Two ways to exist

In-treeMarketplace
Where it livesInside the sebas-bot monorepoIts own public git repository
TrustAutomatic (bot owner owns the repo)Needs explicit owner approval for every new permission
UpdatesVia git pull on the monorepo itself"Update" button in the panel, or auto-update

If you're writing a module to share, the path is always marketplace: your own public repo, see Creating a module.
