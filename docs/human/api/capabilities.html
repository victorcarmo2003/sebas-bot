3. Capabilities

Cinco capabilities reais, cada uma com um entrypoint próprio. Um módulo pode declarar mais de uma.

controller

Superfície HTTP genérica — como o painel fala com a tela de configurações do seu módulo.

interface SebasModuleController {
  handleRequest(ctx, req: SebasControllerRequest): Promise<SebasControllerResponse>;
  selfTest(ctx): Promise<void>;   // chamado uma vez na instalação, em sandbox (sessão 5)
}
interface SebasControllerRequest { method: string; path: string; query: Record<string,string>; headers: Record<string,string>; body: unknown; }
interface SebasControllerResponse { status: number; body: unknown; }

Montado em /api/admin/modules/:seuModuleId/controller/* — req.path já chega sem esse prefixo (uma requisição pra .../permissions/controller/gates/dm chega como req.path = "/gates/dm"). Não existe capability declarativa de UI (apesar de "ui" existir no union de tipos) — você escreve a tela do painel à mão, chamando este controller.

cron

Trabalho periódico em background.

interface SebasModuleChronos { run(ctx): Promise<void>; }

Agendado por manifest.cron.schedule (cron padrão de 5 campos, hora local do host). Roda síncrono até terminar — não existe fila assíncrona separada consumindo trabalho de módulo ainda (a tabela de jobs existe como infra genérica, mas nada drena pra módulo hoje). Faça o polling/trabalho direto dentro de run().

discordCommands

Slash commands.

interface SebasModuleDiscordCommandDefinition { name: string; description: string; }
interface SebasModuleDiscordCommands {
  commands: SebasModuleDiscordCommandDefinition[];
  handleCommand(ctx, commandName: string, interaction: unknown): Promise<{ content: string } | void>;
}

Precisa listar os mesmos nomes em manifest.discordCommands.commands. O core defere a interaction (Discord mostra "pensando...") e chama handleCommand; você termina retornando { content } (edita a resposta deferida sozinho) OU chamando ctx.discord.editInteractionResponse você mesmo e retornando void.

tools

Tools de function-calling que a IA pode chamar.

interface SebasToolDefinition { name: string; description: string; parameters: Record<string, unknown>; } // JSON Schema, formato OpenAI
interface SebasToolCallResult { ok: boolean; result?: unknown; error?: string; }
interface SebasModuleTools {
  tools: SebasToolDefinition[];
  callTool(ctx, name: string, args: Record<string, unknown>): Promise<SebasToolCallResult>;
}

O registry do core qualifica todo nome de tool como module:<seu-id>:<nome> antes de mostrar pra IA — não prefixe você mesmo. Detalhes em sessão 4.

permissionGate

Hook de controle de acesso — usado pelo módulo permissions de referência.

interface PermissionGateRequest {
  discordUserId: string; guildId: string | null; roleIds: string[];
  surface: "dm" | "mention" | "slash_command"; isOwner: boolean;
}
interface PermissionGateResult { canRespond: boolean; allowedTools: string[] | "all"; }
interface SebasModulePermissionGate {
  checkGate(ctx, req: PermissionGateRequest): Promise<PermissionGateResult>;
}

O core chama isso (se um módulo desses estiver instalado e habilitado) antes de responder qualquer DM/menção/slash command, e antes de deixar o agent-loop passar tools pra IA. Sem módulo instalado, ou se ele lançar erro, o core falha seguro: só o dono configurado recebe canRespond=true/allowedTools="all", todo o resto é ignorado silenciosamente.

Implementação de referência completa (modo everyone/whitelist/blacklist por surface, regras por cargo, allowlist global de tools): sebas-module-permissions.

3. Capabilities

Five real capabilities, each with its own entrypoint. A module can declare more than one.

controller

Generic HTTP surface — how the panel talks to your module's settings screen.

interface SebasModuleController {
  handleRequest(ctx, req: SebasControllerRequest): Promise<SebasControllerResponse>;
  selfTest(ctx): Promise<void>;   // called once at install time, sandboxed (section 5)
}
interface SebasControllerRequest { method: string; path: string; query: Record<string,string>; headers: Record<string,string>; body: unknown; }
interface SebasControllerResponse { status: number; body: unknown; }

Mounted at /api/admin/modules/:yourModuleId/controller/* — req.path arrives already stripped of that prefix (a request to .../permissions/controller/gates/dm arrives as req.path = "/gates/dm"). There's no declarative UI capability (despite "ui" existing in the type union) — you hand-write the panel screen, calling this controller.

cron

Periodic background work.

interface SebasModuleChronos { run(ctx): Promise<void>; }

Scheduled per manifest.cron.schedule (standard 5-field cron, host local time). Runs synchronously to completion — there's no separate async job queue consuming module work yet (the jobs table exists as generic infrastructure, but nothing drains it for modules today). Do your polling/work directly inside run().

discordCommands

Slash commands.

interface SebasModuleDiscordCommandDefinition { name: string; description: string; }
interface SebasModuleDiscordCommands {
  commands: SebasModuleDiscordCommandDefinition[];
  handleCommand(ctx, commandName: string, interaction: unknown): Promise<{ content: string } | void>;
}

Must list the same names in manifest.discordCommands.commands. Core defers the interaction (Discord shows "thinking...") and calls handleCommand; you finish by returning { content } (auto-edits the deferred response) OR by calling ctx.discord.editInteractionResponse yourself and returning void.

tools

Function-calling tools the AI can invoke.

interface SebasToolDefinition { name: string; description: string; parameters: Record<string, unknown>; } // JSON Schema, OpenAI format
interface SebasToolCallResult { ok: boolean; result?: unknown; error?: string; }
interface SebasModuleTools {
  tools: SebasToolDefinition[];
  callTool(ctx, name: string, args: Record<string, unknown>): Promise<SebasToolCallResult>;
}

Core's registry qualifies every tool name as module:<your-id>:<name> before showing it to the AI — don't prefix it yourself. Details in section 4.

permissionGate

Access-control hook — used by the reference permissions module.

interface PermissionGateRequest {
  discordUserId: string; guildId: string | null; roleIds: string[];
  surface: "dm" | "mention" | "slash_command"; isOwner: boolean;
}
interface PermissionGateResult { canRespond: boolean; allowedTools: string[] | "all"; }
interface SebasModulePermissionGate {
  checkGate(ctx, req: PermissionGateRequest): Promise<PermissionGateResult>;
}

Core calls this (if such a module is installed and enabled) before answering any DM/mention/slash command, and before letting the agent-loop pass tools to the AI. With no module installed, or if it throws, core fails safe: only the configured owner gets canRespond=true/allowedTools="all", everyone else is silently ignored.

Full reference implementation (everyone/whitelist/blacklist mode per surface, role-based rules, global tool allowlist): sebas-module-permissions.
