4. Tools & Agent Loop

Como a tool do seu módulo chega até o modelo de IA e volta.

O caminho de uma tool call

  1. Cada módulo com capability tools expõe uma lista de SebasToolDefinition.
  2. O ToolRegistry (core) agrega tools de todos os módulos habilitados, mais skills e servidores MCP externos, sob nomes qualificados: module:<seu-id>:<nome-da-tool>.
  3. Quando alguém conversa com o Sebas (DM, menção ou /sebas), o agent-loop manda a mensagem + a lista completa de tools qualificadas pro provedor de IA configurado.
  4. Se o modelo decide chamar uma tool, o agent-loop resolve o nome qualificado de volta pro seu módulo via registry.callQualifiedTool(...), que chama seu callTool(ctx, name, args) com name já sem o prefixo.
  5. O resultado volta pro modelo como uma mensagem role: "tool"; o loop repete até o modelo responder texto final (ou até um teto de iterações).

Filtragem por permissão

Se um módulo permissionGate estiver instalado (sessão 3), allowedTools do resultado do gate filtra quais tools qualificadas chegam até o modelo naquela conversa específica — "all" libera tudo, um array restringe à lista, array vazio significa "só conversa, sem ação".

Shape de request/result do provedor de IA (nível core)

interface AiChatRequest {
  systemPrompt?: string;
  userPrompt?: string;
  messages?: AiChatMessage[];   // historico completo — o agent-loop usa isso, ignora userPrompt
  jsonSchema?: Record<string, unknown>;
  jsonSchemaName?: string;
  maxOutputTokens?: number;
  temperature?: number;
  tools?: SebasToolDefinition[]; // formato OpenAI-compatible
}
interface AiChatResult {
  ok: boolean;
  json?: unknown;
  text?: string;
  toolCalls?: AiToolCall[];
  error?: string;
  providerId: string;
}

Isso é interno ao core (você não monta isso diretamente ao escrever um módulo) — só é útil saber que existe pra entender por que ctx.ai.run() (a versão simplificada que seu módulo usa, ver sessão 2) tem menos campos: o core preenche o resto.

4. Tools & Agent Loop

How your module's tool reaches the AI model and comes back.

A tool call's path

  1. Every module with the tools capability exposes a list of SebasToolDefinition.
  2. Core's ToolRegistry aggregates tools from every enabled module, plus skills and external MCP servers, under qualified names: module:<your-id>:<tool-name>.
  3. When someone talks to Sebas (DM, mention, or /sebas), the agent-loop sends the message plus the full list of qualified tools to the configured AI provider.
  4. If the model decides to call a tool, the agent-loop resolves the qualified name back to your module via registry.callQualifiedTool(...), which calls your callTool(ctx, name, args) with name already without the prefix.
  5. The result goes back to the model as a role: "tool" message; the loop repeats until the model produces a final text answer (or a max-iterations cap is hit).

Permission filtering

If a permissionGate module is installed (section 3), the gate result's allowedTools filters which qualified tools reach the model for that specific conversation — "all" lets everything through, an array restricts to that list, an empty array means "chat only, no actions".

Core-level AI provider request/result shape

interface AiChatRequest {
  systemPrompt?: string;
  userPrompt?: string;
  messages?: AiChatMessage[];   // full history — the agent-loop uses this, ignores userPrompt
  jsonSchema?: Record<string, unknown>;
  jsonSchemaName?: string;
  maxOutputTokens?: number;
  temperature?: number;
  tools?: SebasToolDefinition[]; // OpenAI-compatible format
}
interface AiChatResult {
  ok: boolean;
  json?: unknown;
  text?: string;
  toolCalls?: AiToolCall[];
  error?: string;
  providerId: string;
}

This is internal to core (you don't build this directly when writing a module) — useful mainly to understand why ctx.ai.run() (the simplified version your module uses, see section 2) has fewer fields: core fills in the rest.
